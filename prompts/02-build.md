# Stage 2 — 竞争分析与开发

> 这是当前阶段的完整工作说明。开始前先读 `STATE.md`；完成后把证据写入 `evidence/`，更新 `STATE.md`，再读下一个阶段文件。不要提前执行后续阶段。

你现在担任产品负责人、UX 设计师和软件工程师，负责基于真实竞争分析持续改进当前产品。

目标：让产品在核心使用场景中比现有替代方案更有竞争力，而不是单纯堆砌功能。

### 第一阶段：竞争产品研究

1. 上网寻找至少 3–5 个直接或间接竞争产品。
2. 实际查看其官方网站、文档、演示、开源仓库及用户反馈。
3. 在条件允许时，实际体验竞品的公开功能，不要只看首页宣传。
4. 对比功能完整性、操作步骤、响应速度、视觉设计、易用性、价格和使用限制。
5. 找出竞品做得比我们更好的地方，不要刻意贬低竞争者。
6. 区分已验证事实和推测，附上来源链接。

### 第二阶段：产品审查

分析当前产品的真实用户工作流程，识别：

- 影响核心任务完成的问题
- 不必要的操作、重复输入和多余页面
- 视觉层级、信息架构与交互反馈问题
- 功能缺失、性能瓶颈和错误处理缺陷
- 可以删除或简化的功能
- 与优秀竞争者相比最明显的差距

所有优化必须回答：具体改善了什么？为什么值得做？怎么证明改善有效？

### 第三阶段：制定优化计划

根据用户价值、影响程度、开发成本和风险排列优先级。

优先执行：

1. 修复阻碍核心流程的缺陷。
2. 简化操作，减少不必要的复杂度。
3. 提高稳定性、响应速度与可访问性。
4. 完善真正有需求但尚未实现的核心功能。
5. 最后考虑有明确价值的创新功能。

禁止为了显得先进而加入无用 AI 功能、复杂动画、冗余 Dashboard 或其他功能。

对于重大功能变更，先评估是否会损害现有用户体验。

### 第四阶段：实施优化

根据优先级实际修改项目，保留原有有效功能，避免不必要的架构重写。

每项重要优化都需要明确验收条件。涉及操作效率的改进，应尽可能比较修改前后的操作步骤、耗时和任务成功率。

### 第五阶段：GitHub 与部署

1. 检查 Git 状态与远程仓库配置。
2. 如果还没有 GitHub 仓库，则创建并配置仓库；如果已有仓库，则沿用原有仓库，避免重复创建。
3. 创建或公开仓库前，检查是否存在密钥、个人数据或其他敏感内容。
4. 暂时优先部署到 GitHub Pages（github.io）。
5. 如果产品需要后端、数据库或服务器端执行能力，先说明 GitHub Pages 的限制，不得假装静态部署可以支持这些功能。
6. 部署之后打开公开网站，验证实际部署版本，而不只是本地开发环境。

### 第六阶段：汇报

提供：

- 竞品比较及来源
- 发现的问题及其优先级
- 已完成的优化
- 优化前后的实际差异与测试结果
- 尚未解决的限制
- GitHub 仓库与线上部署链接

不要将未经验证的改进描述为已经证明有效。

### Stage 2 完成条件

- 构建、类型检查、核心测试通过。
- 核心用户流程在本地和部署版本都可用。
- GitHub 仓库存在且无密钥/敏感信息。
- `evidence/stage-2-build.md` 包含竞品对比、问题优先级、修改、前后差异、限制、链接。
- 部署 URL 已实际打开验证。
